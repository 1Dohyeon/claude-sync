# Tasks 관리

## Tasks Flow

### 일반적인 상황

**1. 작업 준비**

```
태스크가 주어짐
→ 새세션 오픈 (Session = Task)
    → `load-progress.js` 훅이 `docs/<repo>/overview.md`
        + 현재 브랜치의 최신 task 기록을 읽음
    → 컨텍스트에 주입 (읽기 전용, 새 세션일 때 고정 실행)
```

- `overview.md` 없으면 Claude는 미리 알고 있음(먼저 언급 가능) / task 파일 없으면 Claude도 모름(물어봐야 확인)
  - 어느 쪽이든 채팅에 자동으로 뜨진 않음
- `.git` 없으면 코딩 작업이 아니라고 판단해 아무 것도 안 함

**2. 설계 시작**

훅 없음. 전부 `CLAUDE.md`의 TASK 기록 규칙에 따라 Claude가 스스로 챙긴다 (Plan 모드 여부와 무관).

```
사용자와 질의응답을 통해 Task 설계를 끝냄 (하나로 충분한지, 두 개 이상으로 나눌지도 이때 결론)
→ 코드를 건드리기 전에 Claude가 직접 `docs/<repo>/tasks/<branch>/YYYYMMDD.md`에 설계 내용을 적음
   (이 시점의 현재 브랜치 = 보통 develop 등 base 브랜치)
   두 개 이상으로 분리됐다면 각 제안 브랜치명으로 각각 만들어 나눠 적음
   (git 브랜치가 아직 없어도 폴더명만으로 작성 가능)
→ Claude가 `feature/<task명>` 브랜치를 생성 (또는 사용자가 직접 생성)
   두 개 이상으로 분리됐다면, 지금 체크아웃된 브랜치를 제외한 나머지는
   `git worktree add`로 별도 디렉터리까지 만듦 (branch만 만들면 병렬 세션이 안 됨)
```

- Plan 모드(`Shift + Tab`)를 탔든 안 탔든 상관없이 적용됨 — 특정 도구 호출에 의존하지 않음
- 분리 시 브랜치별 파일을 미리 나눠두는 이유: 나중에 각 브랜치로 새 세션을 열었을 때 그 세션이 자기 몫의 설계를 처음부터 알고 시작하게 하기 위함 (안 그러면 develop에만 있어서 빈 상태로 시작함)
- worktree가 꼭 필요한 이유: 한 작업 디렉터리는 브랜치를 하나만 체크아웃할 수 있어서, 같은 폴더에서 새 세션만 열면 그 세션도 여전히 원래 브랜치(A)를 보게 됨 — B를 병렬로 작업하려면 B를 위한 별도 worktree 폴더가 반드시 있어야 함

**3. 작업 진행**

```
→ Task가 하나라면 세션 변경 없이 Task 진행
→ 작업 완료로 판단되면 파일 끝에 `## 완료 (HH:MM)` 섹션 추가
```

- 설계자 세션이므로 태스크를 가장 잘 알기에 바로 작업 진행 (단일 Task인 경우)
- Task가 여러개라면 기존 세션은 감독 역할로 전환되고, 사용자는 2번에서 만들어둔 worktree 폴더별로 세션을 새로 생성 (같은 폴더에서 새 세션만 열면 안 됨 — 여전히 원래 브랜치를 봄)
