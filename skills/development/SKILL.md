# 개발 작업 규칙

[`rules/workflow.md`](../../rules/workflow.md) 규칙 위에서 진행되는 개발 작업에서의 규칙이다.

## 규칙 우선순위

- 저장소마다 개발 성격이 다르므로 저장소의 개발 규칙을 이 문서보다 우선한다.
- 저장소 규칙은 그 저장소의 `CLAUDE.md`·`README.md`에서 연결돼 있거나 `.claude/` 아래에 있는 것만 본다. 거기서 찾지 못하면 찾느라 시간을 쓰지 않고 이 문서의 규칙으로만 작업한다.
- 저장소에 커밋되는 문서와 주석에 개인 글로벌 설정(`~/.claude`의 규칙과 스킬)의 내용을 옮기거나 가리키지 않는다. 그 설정이 없는 팀원에게는 틀린 문장이 된다. 사용자가 글로벌 설정을 "참고하라"고 하면 서술 방식만 참고한다.
- 계획 문서([`planning-dev`](../planning-dev/SKILL.md))가 있으면 그 계획을 따른다. 찾는 순서는 [`planning-dev`의 "계획 문서 찾기"](../planning-dev/SKILL.md#계획-문서-찾기)에 있다. 규모가 standard 이상인데 계획이 없으면 planning-dev를 먼저 거치자고 제안한다. 유형과 규모의 정의는 [`planning-dev/sub/analyze-task.md`](../planning-dev/sub/analyze-task.md)에 있다.

## 단순함 우선

- 문제를 푸는 데 필요한 최소한의 코드만 작성한다.
- 요청받지 않은 기능·추상화·설정 가능성을 넣지 않는다.
- 일어날 수 없는 상황에 대한 에러 처리를 넣지 않는다.
- 200줄로 짤 걸 50줄로 짤 수 있으면 다시 짠다.

## 외과적 수정

- 건드려야 하는 곳만 건드린다. 인접 코드·주석·포맷을 "개선"하지 않고, 깨지지 않은 걸 리팩터링하지 않는다.
- 내 방식이 더 낫다고 생각해도 기존 스타일을 따른다.
- 기존 스타일은 표본 한두 개로 판단하지 않는다. 같은 종류의 코드에서 개수를 세어 다수 양식을 따른다. 소수 양식이 한 파일에 몰려 있으면 그 파일의 예외로 본다. 표본이 너무 적으면 다수 양식이 없다고 말한다.
- 관련 없는 죽은 코드를 발견하면 언급만 하고 삭제하지 않는다.
- 이번 변경으로 안 쓰게 된 import·변수·함수만 정리한다. 원래 있던 죽은 코드는 요청 없이 지우지 않는다.
- 바뀐 줄 하나하나가 요청과 직접 연결돼야 한다.

## 주석은 한 곳에만

- 같은 설명을 두 곳 이상에 써야 하면 붙일 곳을 잘못 고른 것이다. 복붙하지 말고, 그 사실이 성립하는 정의 지점(타입·상수·전용 모듈) 한 곳에 쓴다.
- 여러 용도로 공유되는 대상(훅·유틸)에 특정 호출부에서만 참인 설명을 쓰지 않는다. 그런 설명이 필요해졌다는 건 그 사실이 그 대상의 것이 아니라는 신호다.
- 규칙을 의도적으로 어겼으면 근거를 남긴다. 단, 위 두 항목을 지킬 수 있는 위치에만 남긴다.
- 주석에 줄 번호, 파일 경로, 기획서 항목 번호, 개수처럼 바뀔 수 있는 값을 쓰지 않는다. 다른 코드는 함수·심볼 이름이나 동작으로 가리킨다. 그런 값이 필요한 근거는 PR 본문이나 작업 문서에 남긴다.

## 테스트로 검증

코드를 고치기 전에 [`tdd.md`](./tdd.md)를 읽고 그 절차(테스트 먼저, RED 확인, GREEN 확인)를 따른다. 저장소가 테스트 규칙을 따로 두었으면 그것이 먼저다.

## 답이 서지 않는 점

- 구현 중 기획서나 시안으로 답이 서지 않는 점이 나오면 [`planning-dev/sub/plan-docs.md`](../planning-dev/sub/plan-docs.md)의 "결정 기록" 판정으로 가른다.
- 판정을 통과한 것만 임의로 진행하고 `adr.md`·`adr.dev.md`에 남긴다. 통과하지 못한 것은 그 부분을 멈추고 묻는다.
- 서브에이전트는 계획 문서를 고치지 않는다. 임의 진행이 필요해 보이는 결정은 멈춘 뒤 보고하게 하고, 메인이 판정하고 기록한다.

## 서브에이전트 위임

계획 문서가 있고 규모가 standard 이상이면, 1레벨 태스크마다 아래 표로 메인이 직접 할지 [`task-implementer`](../../agents/task-implementer.md)에게 맡길지 가른다. 서브에이전트는 시작할 때마다 저장소 규칙과 계획 문서를 처음부터 다시 읽으므로, 맡기는 횟수만큼 비용이 든다. 규모가 standard 미만이면 메인이 직접 한다.

| 메인이 직접 한다 | 맡긴다 |
| ---------------- | ------ |
| 고칠 파일이 3개 이하이고, 판단 없이 정해진 대로 고치는 태스크(import 경로, 이름 변경, 문구·상수, 확인창 하나 추가 등) | 그 밖의 태스크 |
| 서브에이전트가 보고한 결함 중 고칠 곳과 방법이 보고에 분명히 적힌 것 | |

### 지시

- 지시는 계획 문서 폴더 경로와 태스크 번호(범위)만 넘긴다. 저장소 규칙과 계획 문서는 서브에이전트가 직접 읽는다.

### 순차 진행

- 한 PR 안의 태스크는 순차로 진행한다. 사람이 커밋 단위로 검수할 수 있어야 하므로, 한 PR 안에서 서브에이전트를 동시에 부르지 않는다.
- 맡길 태스크는 이어지는 범위를 서브에이전트 하나에 준다. 서브에이전트가 1레벨 태스크마다 직접 커밋한다.
- 범위와 순서는 `tasks.md`의 `선행:` 줄로 정하고, 서브에이전트가 고칠 파일은 `파일:` 줄로 한정한다.
- 성격이 다른 작업은 [`planning-dev`의 "PR 구조"](../planning-dev/sub/analyze-task.md)에 따라 별도 PR이므로, 각자의 브랜치와 세션에서 동시에 진행할 수 있다.
- 격리 워크트리(`isolation: "worktree"`)는 쓰지 않는다. 기본 시작점이 작업 브랜치가 아니라 원격의 기본 브랜치다.

### 맡긴 범위가 끝난 뒤

1. 메인이 서브에이전트가 만든 커밋의 바꾼 파일이 `파일:` 범위 안인지 `git show --stat`으로 확인한다.
2. 저장소 규칙의 검증 명령(format, lint, 타입 검사, 테스트)을 모두 돌린다.
3. 통과하면 `tasks.md`의 체크박스를 갱신한다.
4. 실패하거나 서브에이전트가 멈춘 것을 보고하면, 원인이 위 "메인이 직접 한다" 기준에 맞을 때는 메인이 고치고 fix 커밋을 남긴다. 그 밖에는 원인 태스크만 다시 맡기거나 사용자에게 보고한다.
5. 하위 PR을 올리기 전에 HEAD에서 저장소 규칙의 검증 명령(format, lint, 타입 검사, 테스트)을 한 번 더 돌린다. 커밋마다 다시 검증하려고 rebase하지 않는다.

## 리뷰·지적

- 코드를 지적하기 전에 요구사항 원문(기획서·이슈·PR 설명)을 먼저 읽는다. 없으면 사용자에게 요청한다.
- 요구사항에 명시된 동작을 "확인 필요"로 올리지 않는다. 코드만 보고 만든 의문은 지적이 아니라 질문이다.
