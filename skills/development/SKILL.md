# 개발 태스크 작업 규칙

[`rules/workflow.md`](../../rules/workflow.md) 규칙 위에서 진행되는 개발 작업에서의 규칙이다.

## 사전 분석

사용자가 코딩 전에 "태스크 분석해줘" 등으로 분석을 요청하면 [`/analyze-task`](../analyze-task/SKILL.md)를 먼저 거친다. 거기서 나온 도메인 설명과 코드 지도를 이후 설계([`worklog.md`](./worklog.md)의 계획 섹션)의 근거로 쓴다.

## 작업 유형과 규모

설계 단계에서 유형과 규모를 한 줄로 밝히고, 사용자가 바꿀 수 있게 한다. task 문서를 만들면 머리 표의 `유형`·`규모` 칸에 적고, 구현 중에 사실이 바뀌면 덮어쓴다. 규모는 [`/analyze-task`](../analyze-task/SKILL.md)가 서브에이전트를 띄울지, [리뷰 공통 절차](../review-common/verify.md)가 어느 축을 부를지 정하는 기준이 된다.

### 유형

유형을 판별하면 해당 파일을 Read하고 그 규칙을 따른다. 이 문서의 규칙은 유형과 관계없이 함께 적용된다.

| 유형 | 판별 기준 | 읽을 파일 |
|---|---|---|
| 새 기능 | 그 기능이 아직 없다 | [`new-feature.md`](./new-feature.md) |
| 동작 변경 | 지금 동작은 정상이지만 원하는 동작이 다르다 | [`change-existing.md`](./change-existing.md) |
| 버그 수정 | 지금 동작이 틀렸다 | [`change-existing.md`](./change-existing.md) |
| 리팩터링 | 동작은 그대로 두고 구조만 바꾼다 | [`change-existing.md`](./change-existing.md) |

### 규모

아래 세 기준 가운데 가장 높게 나온 등급을 따른다.

| 규모 | 수정 파일 | 새 의존성·계약 | 설계상 선택지 |
|---|---|---|---|
| trivial | 1개, 몇 줄 | 없음 | 없음 |
| small | 1개 파일 또는 함수 1개 | 없음 | 코드를 읽으면 분명해진다 |
| standard | 2~5개 | 내부 모듈 정도 | 실제로 골라야 할 선택지가 하나 있다 |
| large | 여러 개, 여러 영역에 걸침 | 외부 의존성, 공개 API, DB 스키마 | 열린 질문이 여럿 있다 |

- 인증·인가, 사용자 입력 처리, DB 쿼리·스키마, 파일 경로, 외부 API 호출, 암호화, 시크릿을 건드리면 파일 수와 관계없이 최소 standard다.
- trivial은 task 문서를 만들지 않고 대화로 보고한다.
- large는 한 PR 단위로 나눌 수 있는지 먼저 검토하고, 나눌 수 있으면 나누자고 제안한다.
- 애매하면 한 단계 위로 본다.

## 단순함 우선

- 문제를 푸는 데 필요한 최소한의 코드만 작성한다.
- 요청받지 않은 기능·추상화·설정 가능성을 넣지 않는다.
- 일어날 수 없는 상황에 대한 에러 처리를 넣지 않는다.
- 200줄로 짤 걸 50줄로 짤 수 있으면 다시 짠다.

## 외과적 수정

- 건드려야 하는 곳만 건드린다. 인접 코드·주석·포맷을 "개선"하지 않고, 깨지지 않은 걸 리팩터링하지 않는다.
- 내 방식이 더 낫다고 생각해도 기존 스타일을 따른다.
- 관련 없는 죽은 코드를 발견하면 언급만 하고 삭제하지 않는다.
- 이번 변경으로 안 쓰게 된 import·변수·함수만 정리한다. 원래 있던 죽은 코드는 요청 없이 지우지 않는다.
- 바뀐 줄 하나하나가 요청과 직접 연결돼야 한다.

## 주석은 한 곳에만

- 같은 설명을 두 곳 이상에 써야 하면 붙일 곳을 잘못 고른 것이다. 복붙하지 말고, 그 사실이 성립하는 정의 지점(타입·상수·전용 모듈) 한 곳에 쓴다.
- 여러 용도로 공유되는 대상(훅·유틸)에 특정 호출부에서만 참인 설명을 쓰지 않는다. 그런 설명이 필요해졌다는 건 그 사실이 그 대상의 것이 아니라는 신호다.
- 규칙을 의도적으로 어겼으면 근거를 남긴다. 단, 위 두 항목을 지킬 수 있는 위치에만 남긴다.

## 테스트로 검증

- 유형별로 어떤 테스트를 먼저 쓰는지는 위 유형 파일에 있다.
- 유효성 검사 추가: 유형과 관계없이 실패 케이스 테스트를 먼저 작성하고 통과시킨다.

## 리뷰·지적

- 코드를 지적하기 전에 요구사항 원문(기획서·이슈·PR 설명)을 먼저 읽는다. 없으면 사용자에게 요청한다.
- 요구사항에 명시된 동작을 "확인 필요"로 올리지 않는다. 코드만 보고 만든 의문은 지적이 아니라 질문이다.

## 기록

기능 추가, 버그 수정, 리팩토링 등 브랜치를 생성하는 작업이면 [`worklog.md`](./worklog.md)를 읽고 그 규칙을 따른다.
