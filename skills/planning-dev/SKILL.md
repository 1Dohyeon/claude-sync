# 개발 계획

코드를 쓰기 전에 무엇을 왜 하는지 정리하는 단계다. 구현은 [`development`](../development/SKILL.md)가 맡는다.

## 1. 요청사항 분석

[`analyze-task.md`](./analyze-task.md)를 읽고 그대로 한다. 태스크의 목적, 유형, 규모, 해야 할 일을 정리해 대화로 보고한다.

## 2. 계획 문서를 만들지 묻는다

분석을 보고한 뒤 계획 문서를 만들면서 진행할지 `AskUserQuestion`으로 묻는다. 문서는 필수가 아니다.

| 선택지                        | 위치                                                                                                                              |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| worklog에 만든다              | `~/.claude/worklog/planning/{owner}/{repo}/{branch}/`                                                                             |
| 하네스가 지정한 위치에 만든다 | 저장소의 `CLAUDE.md`·`README.md`·`.claude/` 등이 계획 문서 위치를 지정해 두었으면 그 폴더. 찾기 어려우면 사용자에게 경로를 받는다 |
| 만들지 않는다                 | 문서 없이 대화로 계획하고 진행한다                                                                                                |

- `{owner}`·`{repo}`는 `git remote get-url origin`에서, `{branch}`는 `git rev-parse --abbrev-ref HEAD`에서 얻는다. 매번 새로 계산한다. 브랜치 이름의 `/`는 폴더 계층이 된다.
- 원격이 없으면 `{owner}/{repo}` 자리에 쓸 이름을 사용자에게 묻는다. 추측하지 않는다.
- `~/.claude/worklog`가 없으면 [`worklog-setup.md`](./worklog-setup.md)를 따른다.
- 그 위치에 이미 문서가 있으면 새로 만들지 않고 이어서 쓴다.

## 3. 세 문서

만들기로 했으면 한 폴더에 세 파일을 둔다. 형식은 아래 역할만 지키고, 나머지는 작업에 맞게 쓴다.

- `requirements.md`: 무엇을 왜 바꾸는가. 사용자도 읽는 문서다.
  - 머리에 유형과 규모를 한 줄로 적는다. 정의는 [`analyze-task.md`](./analyze-task.md)에 있다.
  - 배경은 사용자가 요청과 함께 알려줬을 때만 쓴다. 없으면 적지 않는다.
  - 무엇이 바뀌는지 적는다.
  - 요구사항마다 번호(1, 2, …)를 붙이고, 무엇을 만족하면 끝인지 판정할 수 있는 확인 기준을 함께 적는다.
  - 버그 수정이면 요구사항 안에서 지금 동작, 기대 동작, 바뀌면 안 되는 동작을 나눈다.
- `design.md`: 어떻게 만드는가. 구조, 바뀌는 모듈과 인터페이스, 데이터, 오류 처리, 테스트 전략을 적는다. 테스트 전략은 요구사항 번호마다 무엇을 어떻게 확인할지 적는다.
- `tasks.md`: 어떤 순서로 하는가.
  - 머리에 상태를 적는다. `상태: 진행 중` 또는 `상태: 완료 (YYYY-MM-DD, 사용자 확인)`.
  - 체크박스와 번호로 된 태스크 목록이다. 태스크마다 참조하는 요구사항 번호를 적는다.
  - 테스트를 쓰는 태스크는 그 테스트를 통과시키는 구현 태스크보다 앞에 둔다.

파일 하나를 쓰면 사용자 승인을 받은 뒤 다음 파일로 넘어간다. 사실이 바뀌면 해당 문서를 덮어쓴다.

## 4. 구현

계획이 정해지면 [`development`](../development/SKILL.md)로 넘어간다. 태스크를 끝낼 때마다 `tasks.md`의 체크박스를 갱신한다.

## 5. 완료

- 태스크가 모두 체크돼도 스스로 끝났다고 판단하지 않는다. 끝났는지 사용자에게 묻는다.
- 사용자가 끝났다고 하면 `tasks.md`의 상태를 완료로 바꾼다.
- worklog에 만든 문서면 폴더를 `~/.claude/worklog/planning/done/{owner}/{repo}/{branch}/`로 옮긴다. 같은 경로가 이미 있으면 덮어쓰지 않고 사용자에게 묻는다.
- 하네스가 지정한 위치의 문서는 그 하네스의 완료 규칙을 따른다. 규칙이 없으면 상태만 바꾼다.
