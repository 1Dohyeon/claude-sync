# 요청사항 분석

[`SKILL.md`](../SKILL.md)의 1단계다. 태스크의 목적, 유형, 규모, 해야 할 일을 정리한다. 사용자가 도메인 지식이 적어도 태스크를 이해하도록, 필요하면 도메인 설명과 코드 지도를 만든다.

## 요구사항 확보

분석은 요구사항 원문 위에서만 한다. 원문이 없으면 분석하지 않는다.

| 사용자가 준 것                      | 진행                                                                      |
| ----------------------------------- | ------------------------------------------------------------------------- |
| 태스크 텍스트를 그대로 붙여넣음     | 그 텍스트를 원문으로 삼아 분석을 시작한다.                                |
| 링크를 주었고, 그 링크를 열 수 있음 | 읽어 온 내용을 원문으로 삼아 분석을 시작한다.                             |
| 링크를 주었으나, 열 수 없음         | **분석하지 않는다.** 왜 못 여는지 밝히고 원문을 붙여넣어 달라고 요청한다. |

- Notion 링크는 `notion-fetch`로 읽는다. 다른 링크는 `WebFetch`로 읽는다.
- 도구가 없거나 인증·권한 오류로 열리지 않으면 Claude in Chrome으로 사용자의 브라우저에서 그 링크를 열어 본다. 쓰기 전에 `claude-in-chrome` 스킬을 읽는다. 이것까지 안 되면 "열 수 없음"이다.
- 열 수 있는지 미리 짐작하지 않는다. 한 번 시도해 보고 그 결과로 판정한다.
- **열지 못한 링크의 내용을 제목이나 URL로 미루어 지어내지 않는다.** 멈추는 것이 맞다.
- 링크로 읽어 온 경우에는 무엇을 읽었는지 한 줄로 밝히고 진행한다. 붙여넣은 텍스트는 확인이 필요 없다.
- 페이지가 크면 태스크에 해당하는 절만 추린다. 무관한 부분까지 통째로 다루지 않는다.
- 사용자가 분석 범위를 좁혀줬으면 그것이 1순위다.

## 유형과 규모

요구사항만 보고 유형과 규모를 한 줄로 추정해 밝히고, 사용자가 바꿀 수 있게 한다. 코드 분석에서 드러난 사실이 추정과 다르면 고친다. 다른 스킬(리뷰 등)도 이 정의를 쓴다.

### 유형

| 유형      | 판별 기준                                   |
| --------- | ------------------------------------------- |
| 새 기능   | 그 기능이 아직 없다                         |
| 동작 변경 | 지금 동작은 정상이지만 원하는 동작이 다르다 |
| 버그 수정 | 지금 동작이 틀렸다                          |
| 리팩터링  | 동작은 그대로 두고 구조만 바꾼다            |

### 규모

아래 세 기준 가운데 가장 높게 나온 등급을 따른다.

| 규모     | 수정 파일                 | 새 의존성·계약                   | 설계상 선택지                       |
| -------- | ------------------------- | -------------------------------- | ----------------------------------- |
| trivial  | 1개, 몇 줄                | 없음                             | 없음                                |
| small    | 1개 파일 또는 함수 1개    | 없음                             | 코드를 읽으면 분명해진다            |
| standard | 2~5개                     | 내부 모듈 정도                   | 실제로 골라야 할 선택지가 하나 있다 |
| large    | 여러 개, 여러 영역에 걸침 | 외부 의존성, 공개 API, DB 스키마 | 열린 질문이 여럿 있다               |
| epic     | large 덩어리가 둘 이상    | 다른 팀과의 계약·일정            | 마일스톤 단위로 나눠서 정해야 한다  |

- 인증·인가, 사용자 입력 처리, DB 쿼리·스키마, 파일 경로, 외부 API 호출, 암호화, 시크릿을 건드리면 파일 수와 관계없이 최소 standard다.
- 애매하면 한 단계 위로 본다.

#### 파일 세는 방식

규모의 "수정 파일"과 [`git-workflow`](../../git-workflow/SKILL.md)의 PR 크기 기준이 모두 이 방식으로 센다.

- 구현 파일 하나와 그 파일에만 딸린 짝 파일은 한 개로 센다.
  - 프론트엔드: `index.tsx` + `styles.css.ts` + 테스트 + 스토리
  - 백엔드: `order.service.ts` + `order.service.spec.ts`
  - 공통: 구현 파일 + 그 파일 전용 타입 선언·픽스처
- 여러 파일이 함께 쓰는 파일(공용 타입, 설정, 스키마)은 따로 센다.
- lockfile과 자동 생성 파일은 세지 않는다.

#### epic 판정

아래 가운데 둘 이상에 해당하면 epic이다.

- large 크기의 덩어리가 둘 이상 들어 있다.
- 여러 앱이나 여러 저장소에 걸친다.
- 다른 팀과의 계약이나 일정에 의존한다.
- 한 사람이 몇 주 이상 걸린다.

#### 규모의 용도

- 규모는 PR 구조를 정하는 출발점이자, 리뷰에서 부를 축을 정하는 값이다.
- PR 구조 때문에 규모를 바꾸지 않는다. 부모 구조로 시작했는데 하위 PR이 하나로 끝나도 규모는 그대로 둔다.
- epic은 하위 PR 단위로 리뷰하므로, 리뷰 축은 하위 PR의 규모로 정한다.

### PR 구조

위에서부터 순서대로 판정한다. 구조마다 브랜치·커밋·PR을 다루는 규칙은 [`git-workflow`](../../git-workflow/SKILL.md)의 "커밋·PR 범위"에 있다.

| 순서 | 질문                                                         | 예이면                                                                                                                | 보통 해당하는 규모            |
| ---- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| 1    | 리뷰 단위가 하나로 충분한가?                                 | **단일 PR**: 베이스에서 브랜치를 따고 PR 하나를 베이스로 올린다                                                       | trivial, small, standard 일부 |
| 2    | 조각마다 베이스에 바로 올려도 미완성 상태가 노출되지 않는가? | **순차 PR**: 부모 없이 하위 PR을 순서대로 베이스에 올린다                                                             | standard 일부                 |
| 3    | 위 둘 다 아니다                                              | **부모 PR + 하위 PR**: 베이스에서 부모 브랜치를 만들고 하위 PR을 부모에 머지한 뒤, 모두 모이면 부모를 베이스로 올린다 | standard 일부, large, epic    |

- 부모 브랜치는 미완성 중간 상태를 베이스 대신 담아 두는 곳이다. 그 필요가 있을 때만 만든다.
- 부모 구조로 시작했는데 하위 PR이 하나로 끝나면, 부모에서 바로 베이스로 PR을 올린다.

## 분석과 보고

지금 세션이 요구사항 원문과 관련 코드를 직접 읽고 분석한다.

- 마크다운 보고 하나로 낸다. 태스크의 목적과 해야 할 일, 필요하면 도메인 설명과 코드 지도를 담는다.
- 보고 머리에 추정한 유형과 규모, PR 구조를 적는다. 코드를 읽고 추정과 달라졌으면 고친 값과 이유를 함께 적는다.
- 보고 머리에 작업 브랜치와 베이스도 적는다. 세션의 현재 브랜치가 `feature/*`처럼 이미 작업 브랜치이면(베이스 브랜치 `develop`, `release/*`, `main`이 아니면) 그 이름을 제안하고, 베이스 브랜치이면 저장소의 기존 브랜치 이름 관례(`git branch -r`)를 따라 작업 브랜치 이름을 제안한다. 사용자가 다른 이름을 주면 그 이름을 쓴다. 베이스는 [`git-workflow`](../../git-workflow/SKILL.md)의 "베이스 브랜치 고르기"로 정한다.
- 코드 위치는 `파일:심볼`로 쓴다. 행 번호는 쓰지 않는다.
- "확인이 필요한 질문"은 맨 뒤에 모은다.
- **이 단계의 산출물은 대화로만 낸다. 계획 문서는 여기서 만들지 않는다.**
- 보고를 마치면 [`SKILL.md`](../SKILL.md)의 2단계(계획 문서 위치 정하기)로 넘어간다. 문서를 만들면 이 분석이 `requirements.md`와 `design.md`의 근거가 된다.
