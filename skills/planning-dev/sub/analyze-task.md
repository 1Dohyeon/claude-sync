# 요청사항 분석

[`SKILL.md`](../SKILL.md)의 1단계다. 태스크의 목적, 유형, 규모, 해야 할 일을 정리한다. 사용자가 도메인 지식이 적어도 태스크를 이해하도록, 필요하면 도메인 설명과 코드 지도를 만든다.

## 요구사항 확보

분석은 요구사항 원문 위에서만 한다. 원문이 없으면 분석하지 않는다.

| 사용자가 준 것                      | 진행                                                                      |
| ----------------------------------- | ------------------------------------------------------------------------- |
| 태스크 텍스트를 그대로 붙여넣음     | 그 텍스트를 원문으로 삼아 분석을 시작한다.                                |
| 링크를 주었고, 그 링크를 열 수 있음 | 읽어 온 내용을 원문으로 삼아 분석을 시작한다.                             |
| 링크를 주었으나, 열 수 없음         | **분석하지 않는다.** 왜 못 여는지 밝히고 원문을 붙여넣어 달라고 요청한다. |

- Notion 링크는 `notion-fetch`로 읽는다. 다른 링크는 `WebFetch`로 읽는다.
- 도구가 없거나 인증·권한 오류로 열리지 않으면 Claude in Chrome으로 사용자의 브라우저에서 그 링크를 열어 본다. 쓰기 전에 `claude-in-chrome` 스킬을 읽는다. 이것까지 안 되면 "열 수 없음"이다.
- 열 수 있는지 미리 짐작하지 않는다. 한 번 시도해 보고 그 결과로 판정한다.
- **열지 못한 링크의 내용을 제목이나 URL로 미루어 지어내지 않는다.** 멈추는 것이 맞다.
- 링크로 읽어 온 경우에는 무엇을 읽었는지 한 줄로 밝히고 진행한다. 붙여넣은 텍스트는 확인이 필요 없다.
- 페이지가 크면 태스크에 해당하는 절만 추린다. 무관한 부분까지 통째로 다루지 않는다.
- 사용자가 분석 범위를 좁혀줬으면 그것이 1순위다.

## 유형과 규모

요구사항만 보고 유형과 규모를 한 줄로 추정해 밝히고, 사용자가 바꿀 수 있게 한다. 코드 분석에서 드러난 사실이 추정과 다르면 고친다. 다른 스킬(리뷰 등)도 이 정의를 쓴다.

### 유형

| 유형      | 판별 기준                                   |
| --------- | ------------------------------------------- |
| 새 기능   | 그 기능이 아직 없다                         |
| 동작 변경 | 지금 동작은 정상이지만 원하는 동작이 다르다 |
| 버그 수정 | 지금 동작이 틀렸다                          |
| 리팩터링  | 동작은 그대로 두고 구조만 바꾼다            |

### 규모

아래 세 기준 가운데 가장 높게 나온 등급을 따른다.

| 규모     | 수정 파일                 | 새 의존성·계약                   | 설계상 선택지                       |
| -------- | ------------------------- | -------------------------------- | ----------------------------------- |
| trivial  | 1개, 몇 줄                | 없음                             | 없음                                |
| small    | 5개 이하                  | 없음                             | 코드를 읽으면 분명해진다            |
| standard | 6~20개                    | 내부 모듈 정도                   | 실제로 골라야 할 선택지가 하나 있다 |
| large    | 20개 초과                 | 외부 의존성, 공개 API, DB 스키마 | 열린 질문이 여럿 있다               |
| epic     | large 덩어리가 둘 이상    | 다른 팀과의 계약·일정            | 마일스톤 단위로 나눠서 정해야 한다  |

아래 두 규칙은 리뷰 축을 정할 때만 적용한다. 놓치는 쪽이 더 나쁜 리뷰와 달리, 계획 단계에서 규모를 올리면 분석 서브에이전트만 늘어난다.

- 인증·인가, 사용자 입력 처리, DB 쿼리·스키마, 파일 경로, 외부 API 호출, 암호화, 시크릿을 건드리면 파일 수와 관계없이 최소 standard다.
- 애매하면 한 단계 위로 본다.

#### 파일 세는 방식

규모의 "수정 파일"과 [`git-workflow`](../../git-workflow/SKILL.md)의 PR 크기 기준이 모두 이 방식으로 센다.

- 구현 파일 하나와 그 파일에만 딸린 짝 파일은 한 개로 센다.
  - 프론트엔드: `index.tsx` + `styles.css.ts` + 테스트 + 스토리
  - 백엔드: `order.service.ts` + `order.service.spec.ts`
  - 공통: 구현 파일 + 그 파일 전용 타입 선언·픽스처
- 여러 파일이 함께 쓰는 파일(공용 타입, 설정, 스키마)은 따로 센다.
- lockfile과 자동 생성 파일은 세지 않는다.

#### epic 판정

아래 가운데 둘 이상에 해당하면 epic이다.

- large 크기의 덩어리가 둘 이상 들어 있다.
- 여러 앱이나 여러 저장소에 걸친다.
- 다른 팀과의 계약이나 일정에 의존한다.
- 한 사람이 몇 주 이상 걸린다.

#### 규모의 용도

- 규모는 분석 서브에이전트를 부를지와 리뷰에서 부를 축을 정하는 값이다. PR 구조는 규모가 아니라 아래 "PR 구조"의 성격과 크기로 정한다.
- PR 구조 때문에 규모를 바꾸지 않는다. 부모 구조로 시작했는데 하위 PR이 하나로 끝나도 규모는 그대로 둔다.
- epic은 하위 PR 단위로 리뷰하므로, 리뷰 축은 하위 PR의 규모로 정한다.

### PR 구조

기본은 단일 PR이다. 위에서부터 순서대로 판정한다. 구조마다 브랜치·커밋·PR을 다루는 규칙은 [`git-workflow`](../../git-workflow/SKILL.md)의 "커밋·PR 범위"에 있다.

| 순서 | 질문                                                                                                     | 예이면                                                                                                                |
| ---- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 1    | 성격이 둘 이상인가?                                                                                      | 성격마다 PR을 나눈다. 나눈 PR마다 2번부터 따로 판정한다                                                               |
| 2    | 예상 크기가 [`git-workflow`](../../git-workflow/SKILL.md)의 "변경 종류와 PR 크기" 기준 안에 드는가?      | **단일 PR**: 베이스에서 브랜치를 따고 PR 하나를 베이스로 올린다                                                       |
| 3    | 조각마다 베이스에 바로 올려도 미완성 상태가 노출되지 않는가?                                             | **순차 PR**: 부모 없이 하위 PR을 순서대로 베이스에 올린다                                                             |
| 4    | 2, 3번이 모두 아니다                                                                                     | **부모 PR + 하위 PR**: 베이스에서 부모 브랜치를 만들고 하위 PR을 부모에 머지한 뒤, 모두 모이면 부모를 베이스로 올린다 |

- 성격은 변경의 목적이다. 리뷰어가 따로 승인하거나 반려할 수 있는 단위로 본다.
  - 같은 성격: 한 기능을 이루는 여러 화면, 그 기능의 API와 화면, 그 기능을 위한 공통 컴포넌트와 구조 변경.
  - 다른 성격: 백엔드 계산식 버그 수정과 프론트 어드민 페이지 수정, 기능 추가와 그와 무관한 버그 수정, 일괄 변경과 작성 변경.
- 한쪽이 다른 쪽에 기대는 의존 관계면 같은 성격이다. 병렬로 작업할 수 있는지는 판정 조건이 아니다.
- 화면, 섹션, API 같은 덩어리 단위로 PR을 나누지 않는다. 덩어리는 태스크와 커밋을 나누는 근거다.
- 부모 브랜치는 미완성 중간 상태를 베이스 대신 담아 두는 곳이다. 그 필요가 있을 때만 만든다.
- 부모 구조로 시작했는데 하위 PR이 하나로 끝나면, 부모에서 바로 베이스로 PR을 올린다.

## 분석과 보고

규모가 large 이상이면 지금 세션(메인)은 분류와 취합만 하고, 분석은 서브에이전트가 한다. standard 이하이면 메인이 직접 분석한다.

### 1. 분류

- 원문만 보고 위 "유형과 규모"대로 유형과 규모를 추정한다. 이 단계에서는 코드를 읽지 않는다.
- standard 이하이면 서브에이전트를 부르지 않는다. 메인이 원문과 관련 코드를 직접 읽고 분석한 뒤 아래 "3. 취합"의 판정대로 정리해 "4. 보고"로 간다. 대상 파일이 대부분 특정되는 규모라, 서브에이전트가 처음부터 다시 읽는 비용이 더 크다.

### 2. 서브에이전트 호출

규모가 large 이상이면 아래 에이전트 셋을 **한 응답에서** 동시에 호출한다. 순차로 부르지 않는다.

| 에이전트                                              | 보는 것                                        |
| ----------------------------------------------------- | ---------------------------------------------- |
| [`scope-analyst`](../../../agents/scope-analyst.md)   | 기획 문서만으로 본 작업 범위, 덩어리 사이 의존 |
| [`impact-analyst`](../../../agents/impact-analyst.md) | 기존 기능 영향과 사이드 이펙트                 |
| [`code-analyst`](../../../agents/code-analyst.md)     | 사이드 이펙트를 빼고 기획대로 만드는 방법      |

- 각 호출 프롬프트에 **확보한 요구사항 원문 텍스트를 그대로** 싣는다. 링크나 경로만 넘기지 않는다. 에이전트의 `tools`에 웹·Notion 도구를 넣지 않아서, 링크만 받으면 원문 없이 분석하게 된다.
- 분석 범위를 좁힌 것이 있으면 함께 넘긴다. [`deep-dive.md`](./deep-dive.md)에서 과거 유사 태스크를 찾았으면 그것도 넘긴다.
- 다른 에이전트의 결과는 넘기지 않는다. 각자 자기 축만 보게 한다.

### 3. 취합

모든 결과가 온 뒤에 취합한다. 메인이 새 분석을 덧붙이지 않는다.

- 규모는 분류에서 추정한 값과 에이전트 결과에서 드러난 값 가운데 큰 쪽으로 정한다. 바뀌었으면 이유를 적는다.
- PR 구조는 위 "PR 구조"로 판정한다. `scope-analyst`의 덩어리와 의존, `code-analyst`의 구현 순서, `impact-analyst`의 영향 범위는 태스크와 커밋을 나누는 근거로 쓴다. 크기 기준을 넘어 하위 PR로 나눌 때만 같은 근거로 PR 경계를 잡는다.
- 결론이 서로 다르면 해소하지 않고 나란히 둔다.
- 보고 뒤 사용자가 되묻는 질문은 메인이 직접 답한다. 서브에이전트를 다시 부르지 않는다.

### 4. 보고

마크다운 보고 하나로 낸다. `ReportFindings`는 쓰지 않는다. 아래 순서로 쓴다.

1. 머리: 유형, 규모, PR 구조, 작업 브랜치와 베이스.
2. 작업 범위 요약과 처음 보는 사람이 알아야 할 용어.
3. PR 분할: 다음에 진행할 하위 PR 하나는 범위와 커밋 단위까지, 나머지는 범위와 의존 관계만 적는다. 단일 PR이면 커밋 단위만 적는다.
4. 영향과 리스크.
5. 확인이 필요한 질문.

- 분류에서 추정한 값과 최종 값이 다르면 보고 머리에 고친 값과 이유를 함께 적는다.
- 보고 머리에 작업 브랜치와 베이스도 적는다. 세션의 현재 브랜치가 `feature/*`처럼 이미 작업 브랜치이면(베이스 브랜치 `develop`, `release/*`, `main`이 아니면) 그 이름을 제안하고, 베이스 브랜치이면 저장소의 기존 브랜치 이름 관례(`git branch -r`)를 따라 작업 브랜치 이름을 제안한다. 사용자가 다른 이름을 주면 그 이름을 쓴다. 베이스는 [`git-workflow`](../../git-workflow/SKILL.md)의 "베이스 브랜치 고르기"로 정한다.
- 코드 위치는 `파일:심볼`로 쓴다. 행 번호는 쓰지 않는다.
- "확인이 필요한 질문"은 맨 뒤에 모은다.
- **이 단계의 산출물은 대화로만 낸다. 계획 문서는 여기서 만들지 않는다.**
- 보고를 마치면 [`SKILL.md`](../SKILL.md)의 2단계(계획 문서 위치 정하기)로 넘어간다. 문서를 만들면 이 분석이 `requirements.md`와 `design.md`의 근거가 된다.
