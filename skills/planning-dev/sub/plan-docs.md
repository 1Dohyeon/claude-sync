# 계획 문서

[`SKILL.md`](../SKILL.md)의 2, 3단계다. 계획 문서를 어디에 둘지 정하고, 세 문서를 쓴다.

## 위치 정하기

분석을 보고한 뒤 새 계획 문서를 어디에 둘지 **꼭** `AskUserQuestion`으로 묻는다. 선택지는 아래 순위대로 둔다.

| 순위 | 선택지                    | 위치                                                                                                                                                     |
| ---- | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 앱의 훅이 안내하는 위치   | 세션을 연 앱이 훅(세션 시작 안내)으로 안내하는 경로. 형식도 그 안내를 따른다                                                                             |
| 2    | 사용자 지정 위치          | `$PLANS_PATH/{owner}/{repo}/{branch}/`. `PLANS_PATH`의 값은 [`rules/environments.md`](../../../rules/environments.md)에 있다                             |
| 3    | 저장소 문서가 지정한 위치 | 저장소의 `CLAUDE.md`·`README.md`·`.claude/`가 지정한 경로. 이 세 곳만 읽고 그 밖은 찾지 않는다. 형식도 그 문서를 따른다                                 |
| 4    | 대화로 계획               | 시스템 프롬프트에 적힌 scratchpad 경로 아래에 쓴다. 설계대로 진행하지만, 세션을 끝내면 이어받을 수 없어 다시 설계해야 한다. 선택지 설명에 이 결과를 적는다 |

- 1순위나 3순위의 안내가 없으면 그 순위를 빼고 묻는다.
- 경로 문자열이 완전히 같은 선택지끼리는 한 선택지로 합친다. 심링크처럼 문자열이 다르면 실제로 같은 폴더여도 따로 둔다.
- `{owner}`·`{repo}`는 `git remote get-url origin`에서 얻는다. 매번 새로 계산한다.
- `{branch}`는 1단계 보고에서 정한 작업 브랜치 이름이다. 여기서 다시 정하지 않는다. 브랜치 이름의 `/`는 폴더 계층이 된다.
  - 그 브랜치가 아직 없어도 계획 문서를 먼저 만든다. 브랜치는 3단계 이후 만들자고 제안한다. ([`git-workflow`](../../git-workflow/SKILL.md) 참고)

### git 원격이 없다면
- `_local/` 경로에 작성한다. `{owner}` 자리에 `_local`을 쓴다: `$PLANS_PATH/_local/{repo}/{branch}/`
- `{repo}`는 저장소 최상위 폴더 이름(`git rev-parse --show-toplevel`의 마지막 경로)이다.
- 같은 이름의 `_local/{repo}/`가 이미 있는데 다른 저장소의 문서로 보이면, 덮어쓰지 않고 쓸 이름을 사용자에게 묻는다.
- git 저장소가 아니라 브랜치가 없으면 `{branch}` 자리에 1단계에서 정한 작업 이름을 쓴다.
- 나중에 원격이 생기면 폴더를 `{owner}/{repo}/` 아래로 옮긴다. 옮기기 전까지는 "계획 문서 찾기"가 원격 기준 경로에서 찾지 못한다.

### 참고
- `$PLANS_PATH`가 없는 기기에서 2순위를 고르면 그 폴더부터 새로 만든다.
- 시스템 프롬프트에 scratchpad 경로가 없는 환경에서 4순위를 고르면 파일 없이 대화로만 계획하고 진행한다.

## 세 문서

만들기로 했으면 한 폴더에 세 파일을 둔다. 형식은 아래 역할만 지키고, 나머지는 작업에 맞게 쓴다. `design.md`와 `tasks.md`를 쓰기 전에 [`development/tdd.md`](../../development/tdd.md)를 읽는다.

- `requirements.md`: 무엇을 왜 바꾸는가. 사용자도 읽는 문서다.
  - 머리에 유형과 규모를 한 줄로 적는다. 정의는 [`analyze-task.md`](./analyze-task.md)에 있다.
  - 그다음 줄에 `브랜치: <브랜치> (베이스: <베이스>)`를 적는다. worktree 생성과 브랜치 리뷰가 이 줄을 읽는다.
  - 배경은 사용자가 요청과 함께 알려줬을 때만 쓴다. 없으면 적지 않는다.
  - 무엇이 바뀌는지 적는다.
  - 요구사항마다 번호(1, 2, …)를 붙이고, 무엇을 만족하면 끝인지 판정할 수 있는 확인 기준을 함께 적는다.
  - 버그 수정이면 요구사항 안에서 지금 동작, 기대 동작, 바뀌면 안 되는 동작을 나눈다.
- `design.md`: 어떻게 만드는가. 구조, 바뀌는 모듈과 인터페이스, 데이터, 오류 처리, 테스트 전략을 적는다. 테스트 전략은 요구사항 번호마다 테스트로 확인할지, 실행해서 확인할지와 그 방법을 적는다.
- `tasks.md`: 어떤 순서로 하는가.
  - 머리에 상태를 적는다. `상태: 진행 중` 또는 `상태: 완료 (YYYY-MM-DD, 사용자 확인)`.
  - 그다음 줄에 PR 구조(단일 PR, 순차 PR, 부모 PR + 하위 PR)를 적는다. 판정은 [`analyze-task.md`](./analyze-task.md)의 "PR 구조"에 있다.
  - 순차 PR이나 부모 PR + 하위 PR이면, 지금 진행할 하위 PR 하나만 태스크로 쪼갠다. 나머지는 마일스톤과 의존 관계만 적고, 그 하위 PR을 올릴 때 다음 하위 PR의 태스크를 적는다.
  - 체크박스와 번호로 된 태스크 목록이다. 태스크마다 참조하는 요구사항 번호를 적는다.
  - 1레벨 체크박스 하나는 커밋 하나다. 서브에이전트에게 한 번 넘겨 끝낼 수 있고, 그 안에서 검증(테스트, 타입 검사)까지 마칠 수 있는 크기로 쪼갠다. 커밋 기준은 [`git-workflow`](../../git-workflow/SKILL.md)의 "커밋·PR 범위"에 있다.
  - 1레벨 태스크마다 바로 아래에 `파일:`(고칠 파일·폴더)과 `선행:`(먼저 끝나야 하는 태스크 번호, 없으면 `없음`)을 체크박스 없는 줄로 적는다. 구현 단계에서 병렬로 묶을 태스크를 이 두 줄로 고른다([`development`](../../development/SKILL.md)의 "서브에이전트 위임").
  - 1레벨 태스크 안의 단계는 2레벨로 적고, `tdd.md`의 절차 순서를 따른다. 테스트 작성과 RED 확인 단계를 그 테스트를 통과시키는 구현과 GREEN 확인 단계보다 앞에 둔다.
  - `tdd.md`의 적용 범위 밖이라 실행해서 확인할 항목은 확인 태스크로 따로 적는다.

세 문서를 모두 쓴 뒤 한 번에 확인받는다. 문서마다 따로 승인을 받지 않는다.

- 확인을 요청할 때 세 문서의 핵심을 보고 하나로 요약한다. 요구사항 번호와 확인 기준을 맨 앞에 두고, 설계에서 고른 선택지와 이유, PR 구조, 태스크 순서와 커밋 단위를 그 뒤에 둔다. 사용자가 판단해야 할 결정은 맨 뒤에 모은다.
- 수정 요청을 받으면 그 문서만 고치지 않고, 영향을 받는 나머지 문서도 함께 맞춘 뒤 다시 한 번에 확인받는다.
- 확인을 받기 전에는 구현으로 넘어가지 않는다.
- 사실이 바뀌면 해당 문서를 덮어쓴다.
