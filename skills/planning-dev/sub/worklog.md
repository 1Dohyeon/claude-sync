# 계획 문서

[`SKILL.md`](../SKILL.md)의 2, 3단계다. 계획 문서를 어디에 둘지 정하고, 세 문서를 쓴다.

## 위치 정하기

분석을 보고한 뒤 계획 문서를 어디에 두고 진행할지 `AskUserQuestion`으로 묻는다. worklog에 남기는 것은 필수가 아니다.

| 선택지                        | 위치                                                                                                                              |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| worklog에 만든다              | `~/worklog/planning/{owner}/{repo}/{branch}/`                                                                                     |
| 하네스가 지정한 위치에 만든다 | 저장소의 `CLAUDE.md`·`README.md`·`.claude/` 등이 계획 문서 위치를 지정해 두었으면 그 폴더. 찾기 어려우면 사용자에게 경로를 받는다 |
| 세션 임시 폴더에 만든다       | 시스템 프롬프트에 적힌 scratchpad 경로 아래. 세션이 끝나면 이어받을 수 없다                                                       |

- `{owner}`·`{repo}`는 `git remote get-url origin`에서 얻는다. 매번 새로 계산한다.
- `{branch}`는 1단계 보고에서 정한 작업 브랜치 이름이다. 여기서 다시 정하지 않는다. 브랜치 이름의 `/`는 폴더 계층이 된다.
  - 그 브랜치가 아직 없어도 계획 문서를 먼저 만든다. 브랜치는 3단계 이후 만들자고 제안한다. ([`git-workflow`](../../git-workflow/SKILL.md) 참고)

### git 원격이 없다면
- `_local/` 경로에 작성한다. `{owner}` 자리에 `_local`을 쓴다: `~/worklog/planning/_local/{repo}/{branch}/`
- `{repo}`는 저장소 최상위 폴더 이름(`git rev-parse --show-toplevel`의 마지막 경로)이다.
- 같은 이름의 `_local/{repo}/`가 이미 있는데 다른 저장소의 문서로 보이면, 덮어쓰지 않고 쓸 이름을 사용자에게 묻는다.
- git 저장소가 아니라 브랜치가 없으면 `{branch}` 자리에 1단계에서 정한 작업 이름을 쓴다.
- 나중에 원격이 생기면 폴더를 `{owner}/{repo}/` 아래로 옮긴다. 옮기기 전까지는 "계획 문서 찾기"가 원격 기준 경로에서 찾지 못한다.

### 참고
- `~/worklog`가 없는 기기에서 worklog를 고르면 `~/worklog`부터 새로 만든다. git 저장소로 둘지는 사용자가 정하며, git 저장소가 아니어도 계획 문서는 그대로 쓸 수 있다.
- 시스템 프롬프트에 scratchpad 경로가 없는 환경이면 세션 임시 폴더를 선택지에서 빼고, 사용자가 둘 다 원하지 않으면 문서 없이 대화로 계획하고 진행한다.

## 세 문서

만들기로 했으면 한 폴더에 세 파일을 둔다. 형식은 아래 역할만 지키고, 나머지는 작업에 맞게 쓴다. `design.md`와 `tasks.md`를 쓰기 전에 [`development/tdd.md`](../../development/tdd.md)를 읽는다.

- `requirements.md`: 무엇을 왜 바꾸는가. 사용자도 읽는 문서다.
  - 머리에 유형과 규모를 한 줄로 적는다. 정의는 [`analyze-task.md`](./analyze-task.md)에 있다.
  - 그다음 줄에 `브랜치: <브랜치> (베이스: <베이스>)`를 적는다. worktree 생성과 브랜치 리뷰가 이 줄을 읽는다.
  - 배경은 사용자가 요청과 함께 알려줬을 때만 쓴다. 없으면 적지 않는다.
  - 무엇이 바뀌는지 적는다.
  - 요구사항마다 번호(1, 2, …)를 붙이고, 무엇을 만족하면 끝인지 판정할 수 있는 확인 기준을 함께 적는다.
  - 버그 수정이면 요구사항 안에서 지금 동작, 기대 동작, 바뀌면 안 되는 동작을 나눈다.
- `design.md`: 어떻게 만드는가. 구조, 바뀌는 모듈과 인터페이스, 데이터, 오류 처리, 테스트 전략을 적는다. 테스트 전략은 요구사항 번호마다 테스트로 확인할지, 실행해서 확인할지와 그 방법을 적는다.
- `tasks.md`: 어떤 순서로 하는가.
  - 머리에 상태를 적는다. `상태: 진행 중` 또는 `상태: 완료 (YYYY-MM-DD, 사용자 확인)`.
  - 체크박스와 번호로 된 태스크 목록이다. 태스크마다 참조하는 요구사항 번호를 적는다.
  - 태스크는 `tdd.md`의 절차 순서로 쪼갠다. 테스트 작성과 RED 확인 태스크를 그 테스트를 통과시키는 구현과 GREEN 확인 태스크보다 앞에 둔다.
  - `tdd.md`의 적용 범위 밖이라 실행해서 확인할 항목은 확인 태스크로 따로 적는다.

세 문서를 모두 쓴 뒤 한 번에 확인받는다. 문서마다 따로 승인을 받지 않는다.

- 확인을 요청할 때 세 문서의 핵심을 보고 하나로 요약한다. 요구사항 번호와 확인 기준을 맨 앞에 두고, 설계에서 고른 선택지와 이유, 태스크 순서와 커밋 단위를 그 뒤에 둔다. 사용자가 판단해야 할 결정은 맨 뒤에 모은다.
- 수정 요청을 받으면 그 문서만 고치지 않고, 영향을 받는 나머지 문서도 함께 맞춘 뒤 다시 한 번에 확인받는다.
- 확인을 받기 전에는 구현으로 넘어가지 않는다.
- 사실이 바뀌면 해당 문서를 덮어쓴다.
