# 로컬 커밋 리뷰

작업 브랜치에 쌓였지만 아직 push하지 않은 커밋이 대상이다. 판단할 것은 "이대로 push해도 되는가"다. 작업 브랜치와 작업 폴더는 [`review-pr/verify.md`](../review-pr/verify.md#작업-브랜치-정하기)의 "작업 브랜치 정하기"로 정한 것을 쓴다.

## 범위

범위는 "push하지 않은 커밋 전부"다. 커밋하지 않은 변경은 범위에 넣지 않는다. 되묻지 않는다.

비교 기준은 작업 브랜치의 원격 브랜치 `origin/<작업 브랜치>`다. upstream 설정은 보지 않는다. 먼저 원격 상태를 받아 온다.

```sh
git -C <작업 폴더> fetch origin
```

원격 브랜치가 없으면(아직 한 번도 push하지 않았으면) 아래 스냅샷 명령이 `unknown revision` 오류로 실패한다. 그때는 베이스와의 갈림점을 비교 기준으로 쓴다. 베이스는 [`git-worktree`](../git-worktree/SKILL.md)의 "select base"로 정한다.

```sh
git -C <작업 폴더> merge-base origin/<base> HEAD
```

스냅샷은 비교 기준과 `HEAD`를 비교한다. 끝의 `HEAD`를 빠뜨리면 커밋하지 않은 변경까지 섞여 들어온다.

```sh
git -C <작업 폴더> diff <비교 기준> HEAD
```

- 출력이 비어 있으면 push하지 않은 커밋이 없는 것이다. 리뷰할 것이 없다고 알리고 멈춘다.
- 커밋하지 않은 변경은 아래로 확인해서, 있으면 리뷰 범위에서 빠진다는 사실을 알린다. 그 변경을 보려면 먼저 커밋해야 한다.

```sh
git -C <작업 폴더> status --porcelain
```

셸 변수를 쓰지 않고 명령을 리터럴로 쓴다. Bash 호출 사이에는 셸 상태가 남지 않는다. 단일 명령으로 유지한다. `&&`·`;`·`|`로 엮으면 allowlist의 접두 규칙에 걸리지 않아 매번 승인 프롬프트가 뜬다.

## 축

세 축만 부른다. 규모가 trivial이면 [`verify.md`](../review-pr/verify.md)의 "규모 판단"대로 서브에이전트를 부르지 않고 상위가 직접 본다.

- [`logic-reviewer`](../../agents/logic-reviewer.md)
- [`impact-reviewer`](../../agents/impact-reviewer.md)
- [`convention-reviewer`](../../agents/convention-reviewer.md)

**부르기 전에 요구사항을 먼저 확보한다.** 작업 브랜치의 계획 문서 `requirements.md`에서 요구사항을 꺼내 세 에이전트에 실어 넘긴다. 문서가 없으면 커밋 메시지·이번 대화에서 모으고, 그래도 없을 때만 사용자에게 묻는다. 확보 절차는 [`verify.md`](../review-pr/verify.md)의 요구사항 확보에 있다.

여기서 요구사항은 지적을 만드는 근거가 아니라 **오탐을 거르는 근거**다. 공통부 검증의 "요구사항에 명시된 동작은 버린다"가 그것으로 작동한다.

화면에 닿는 파일이 있으면 [`qa-reviewer`](../../agents/qa-reviewer.md)를 부록으로 함께 부른다. 방금 짠 화면을 브라우저에서 무엇부터 볼지가 이 시점의 실제 필요다.

아키텍처·테스트·요구사항 축은 여기서 부르지 않는다. push 직전은 기능이 절반만 짜인 상태일 수 있기 때문이다. 아키텍처 축은 미완성을 구조 결함으로 오인하고, 요구사항 축은 아직 안 만든 것을 누락으로 자리만 잡아둔 코드를 어긋남으로 올린다. 테스트 축은 변경에 대응하는 테스트가 있는지를 완성된 단위에서 봐야 판정이 선다. push 전 커밋에는 [`dev-tdd`](../dev-tdd/SKILL.md)의 절차를 나눠 올린 테스트만 있거나 구현만 있을 수 있고, 테스트 러너가 없어 실행으로 확인하는 저장소도 있어서, 그 범위만 보면 "없다"는 오탐이 쌓인다. 셋 다 [`review-pr`](../review-pr/SKILL.md)가 완성된 단위에서 본다.

반면 `impact-reviewer`는 미완성 상태에서도 부른다. 이미 바꾼 심볼의 호출부는 실재하므로 판정에 추측이 끼지 않고, 방금 고친 것이 다른 곳을 깨뜨렸는지가 push 직전에 가장 알고 싶은 것이기 때문이다.

## 이어서

[`verify.md`](../review-pr/verify.md)를 읽고 요구사항 확보부터 출력까지 그대로 진행한다. 요구사항은 사용자에게 먼저 묻지 않고 작업 브랜치의 계획 문서부터 본다.
