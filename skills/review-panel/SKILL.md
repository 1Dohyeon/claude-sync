# 리뷰 패널 절차

한 모델이 여러 영역을 한 컨텍스트에서 순차로 보면 앞 영역이 뒤 영역 판단에 섞인다.
이 절차는 영역별로 격리된 리뷰어를 병렬로 돌리고, 취합만 상위 모델이 한다. 아래 순서대로 진행한다.

## 리뷰 대상 확정

리뷰 범위는 **사용자가 지정한 것만** 쓴다. 추론하지 않는다.

사용자 메시지(`/review-panel` 뒤에 붙은 인자 포함)에서 아래 넷 중 하나를 찾는다.

| 사용자가 말한 것 | 확정 명령 |
|---|---|
| 커밋 범위 ("A부터 B까지", "이 커밋만", "최근 머지") | `git diff <from> <to>` |
| PR ("3번 PR 리뷰해줘", PR 링크) | `gh pr diff <번호>` |
| 커밋 전 변경 ("커밋 전 파일만", "지금 작업한 것") | `git diff HEAD` |
| 브랜치 전체 ("이 브랜치 리뷰해줘") | `git diff <merge-base SHA> HEAD` |

- 넷 중 어느 것도 찾지 못하면 **패널을 띄우지 말고 사용자에게 범위를 묻는다.** 베이스 브랜치를 추측해서 진행하지 않고, 위 표의 네 가지를 선택지로 제시한다.
- 확정한 명령을 직접 한 번 실행해서 diff가 비어 있지 않은지 확인한다. 비었으면 중단하고 그 사실만 보고한다.

### 명령을 만들 때

- **셸 변수를 쓰지 않고** ref와 SHA를 명령에 리터럴로 박는다. Bash 호출 사이에는 셸 상태가 남지 않아서 `MB=$(...)` 뒤에 쓴 `$MB`는 빈 문자열이 되고, 그러면 `git diff`로 축약되어 에러 없이 전혀 다른 범위를 리뷰하게 된다.
- 단일 명령으로 유지한다. `&&`·`;`·`|`로 엮으면 allowlist의 접두 규칙에 걸리지 않아 매번 승인 프롬프트가 뜬다.
- `git status --porcelain`으로 추적되지 않은 파일(`??`)이 있는지 본다. `git diff`는 그것을 담지 못하므로, 있으면 사용자에게 알리고 포함할지 묻는다.

### PR을 고른 경우

`gh pr diff <번호>`로 diff는 얻을 수 있으나, 리뷰어가 주변 구조와 컨벤션을 대조하려면 디스크의 파일도 그 PR 브랜치여야 한다.

```sh
gh pr view <번호> --json headRefName,state
```

- 현재 체크아웃된 브랜치가 `headRefName`과 같으면 그대로 진행한다.
- 다르면 사용자에게 알리고 고르게 한다: `gh pr checkout <번호>`를 실행할지, 아니면 diff만으로 진행할지. 임의로 체크아웃하지 않는다.
- diff만으로 진행하면 아키텍처·컨벤션 축의 정확도가 떨어지므로 그 사실을 리포트에 적는다.

### 브랜치 전체를 고른 경우

베이스에서 갈라진 뒤 **이 브랜치에 쌓인 커밋 전부**가 대상이다. 아래 순서로 잡는다.

1. 베이스를 정한다. `origin/develop`이 있으면 그것, 없으면 `origin/main`이다. 로컬 `develop`은 쓰지 않는다. worktree로 작업하는 동안 갱신되지 않아 뒤처지기 쉽고, 그러면 갈라진 지점이 과거로 밀려 남의 커밋까지 대상에 들어온다.

```sh
git branch -r
```

2. 갈라진 지점을 구한다. 출력된 SHA를 다음 명령에 리터럴로 옮겨 적는다.

```sh
git merge-base origin/develop HEAD
```

3. **대상 커밋 목록을 사용자에게 보여주고 맞는지 확인받는다.** 낯선 커밋이 섞여 있으면 갈라진 지점을 잘못 잡은 것이므로 중단하고 보고한다. 확인 없이 다음으로 넘어가지 않는다.

```sh
git log --oneline 9a3f1c2..HEAD
```

4. 확정 명령은 아래와 같다. 끝의 `HEAD`를 빠뜨리면 커밋되지 않은 워킹트리 변경까지 섞여 들어와 "커밋 전 변경" 선택지와 범위가 겹친다.

```sh
git diff 9a3f1c2 HEAD
```

5. 커밋되지 않은 변경은 이 범위에 들어가지 않는다. `git status --porcelain`으로 확인해서, 있으면 리뷰 대상에서 빠진다는 사실을 사용자에게 알린다.

## 규모 판단

- 로직이 있는 파일이 하나도 없으면(설정값·문구·주석·경로·문서 수정 등) 패널을 띄우지 않는다. 변경이 여러 파일에 걸쳐도 마찬가지이며, 관련된 한두 영역만 직접 간단히 보고 끝낸다.
- 그 외에는 병렬 호출로 간다.

## 병렬 호출

**한 응답에서** 서브에이전트 4개를 동시에 호출한다. 순차로 부르지 않는다.

- [`architecture-reviewer`](../../agents/architecture-reviewer.md)
- [`logic-reviewer`](../../agents/logic-reviewer.md)
- [`testing-reviewer`](../../agents/testing-reviewer.md)
- [`convention-reviewer`](../../agents/convention-reviewer.md)

각 호출 프롬프트에 다음을 그대로 넘긴다.

- **확정한 diff 명령 전체를 리터럴로** 넘긴다(예: `git diff 9a3f1c2 HEAD`, `gh pr diff 214`). 각 에이전트는 그 명령을 그대로 실행해 동일한 diff를 얻으며, 범위를 다시 추론하게 두지 않는다.
- 추적되지 않은 파일을 포함하기로 했으면 그 경로 목록도 함께 넘긴다.
- "자기 영역만 보고 다른 영역은 지적으로 세우지 말 것" - 각 에이전트 정의에 이미 있으나 한 번 더 못박는다.

## 취합

네 결과가 다 온 뒤에 한다. 이 단계에서 **새로운 지적을 만들지 않는다.**

- 같은 지적이 둘 이상 에이전트에서 나오면 하나로 합치고, 어느 영역들에서 나왔는지 적는다.
- 심각도로 정렬한다. 리뷰어마다 심각도 표기가 다를 수 있으니 전부 높음·중간·낮음으로 정규화한다.
- 에이전트 간 결론이 상반되면 **해소하지 말고 양쪽을 나란히 드러낸다** - 판단은 사용자 몫이다.

## 출력

마크다운 리포트 하나로 낸다. `ReportFindings` 도구는 쓰지 않는다.

- 영역별(아키텍처 / 코드 레벨 / 테스트 / 컨벤션)로 묶고, 그 안에서 심각도 순으로 나열한다.
- 각 항목은 위치(`file:line`), 문제, 제안. logic 항목은 실패 시나리오를 포함한다.
- 영역에 지적이 없으면 "지적 없음"으로 표기하고 그 영역이 무엇을 확인했는지 한 줄 남긴다.
- 마지막에 에이전트 간 상반된 결론이 있었으면 따로 모아 적는다.
