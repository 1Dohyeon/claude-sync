# 태스크 사전 분석 절차

`/development`로 코드를 짜기 전 단계다. 사용자가 도메인 지식이 적어도 태스크를 이해하도록, 도메인 설명과 코드 지도를 미리 만든다.

축을 격리해 병렬로 돌리고 취합만 상위가 하는 구조는 `review-panel`과 같다 — 근거와 세부 규칙은 그쪽을 따른다. 아래는 이 절차에서 다른 점만 적는다.

## 요구사항 확보

- 요구사항 원문(이슈·기획서·설명)을 먼저 읽는다. 없으면 사용자에게 요청한다 — 추측으로 분석하지 않는다.
- 사용자가 분석 범위를 좁혀줬으면 그것이 1순위다.

## 규모 판단

- 요구사항이 한두 문장이고 건드릴 곳이 자명하면 에이전트를 띄우지 않는다. 관련된 것만 직접 짧게 짚고 끝낸다.
- 그 외에는 병렬 호출로 간다.

## 병렬 호출

**한 응답에서** `domain-analyst`와 `code-analyst`를 동시에 호출한다. 각 호출 프롬프트에 확보한 요구사항 원문(또는 그 위치)과 분석 범위를 넘긴다.

## 취합과 출력

두 결과가 다 온 뒤에 한다. 새로운 분석을 만들지 않는다.

- 마크다운 보고 하나로 낸다. 도메인 설명을 앞에, 코드 분석을 뒤에. `ReportFindings`는 쓰지 않는다.
- 코드 파트의 위치는 `파일:심볼`로 쓴다. 행 번호는 쓰지 않는다.
- 두 결론이 상반되면 해소하지 말고 양쪽을 나란히 둔다. 양쪽에서 나온 "확인이 필요한 질문"은 맨 뒤에 하나로 모은다.
- **`domain-analyst`의 산출물은 최종본이 아니라, 상위가 사용자에게 풀어줄 1차 자료다.** 취합 뒤 사용자가 되묻는 후속 질의응답은 상위가 직접 한다 — 서브에이전트를 다시 부르지 않는다.
- **이 단계의 산출물은 대화로만 낸다. worklog 문서를 만들지 않는다.**
- 사용자가 이어서 "설계해줘" 하면 `/task`로 넘어가고, 이 분석이 계획 섹션의 근거가 된다.
