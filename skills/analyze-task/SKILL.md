# 태스크 사전 분석 절차

[`/development`](../development/SKILL.md)로 코드를 짜기 전 단계다. 사용자가 도메인 지식이 적어도 태스크를 이해하도록, 도메인 설명과 코드 지도를 미리 만든다.

축을 격리해 병렬로 돌리고 취합만 상위가 하는 구조는 리뷰 스킬([`diff-review`](../diff-review/SKILL.md)·[`branch-review`](../branch-review/SKILL.md)·[`pr-review`](../pr-review/SKILL.md))과 같고, 그 구조를 두는 이유는 [`review-common/verify.md`](../review-common/verify.md) 서두에 있다. 다만 대상을 확정하는 방식은 다르다. 리뷰 스킬은 각자 정해진 diff 범위를 잡고, 이쪽은 요구사항 원문을 확보한다.

## 요구사항 확보

분석은 요구사항 원문 위에서만 한다. 원문이 없으면 분석하지 않는다.

| 사용자가 준 것 | 진행 |
|---|---|
| 태스크 텍스트를 그대로 붙여넣음 | 그 텍스트를 원문으로 삼아 분석을 시작한다. |
| 링크를 주었고, 그 링크를 열 수 있음 | 읽어 온 내용을 원문으로 삼아 분석을 시작한다. |
| 링크를 주었으나, 열 수 없음 | **분석하지 않는다.** 왜 못 여는지 밝히고 원문을 붙여넣어 달라고 요청한다. |

- Notion 링크는 `notion-fetch`로 읽는다. 도구가 없거나 인증·권한 오류가 나면 "열 수 없음"이다.
- 열 수 있는지 미리 짐작하지 않는다. 한 번 시도해 보고 그 결과로 판정한다.
- **열지 못한 링크의 내용을 제목이나 URL로 미루어 지어내지 않는다.** 멈추는 것이 맞다.
- 링크로 읽어 온 경우에는 무엇을 읽었는지 한 줄로 밝히고 진행한다. 붙여넣은 텍스트는 확인이 필요 없다.
- 페이지가 크면 태스크에 해당하는 절만 추린다. 무관한 부분까지 통째로 서브에이전트에 넘기지 않는다.
- 사용자가 분석 범위를 좁혀줬으면 그것이 1순위다.

## 규모 판단

- 요구사항만 보고 유형과 규모를 한 줄로 추정해 밝힌다. 정의는 [`development`](../development/SKILL.md)의 "작업 유형과 규모"에 있다. 이 값은 추정이고, 이후 설계에서 확정한다.
- trivial·small이면 에이전트를 띄우지 않는다. 관련된 것만 직접 짧게 짚고 끝낸다.
- standard·large이면 병렬 호출로 간다. **병렬 호출로 가는 경우에만** 아래 "과거 유사 태스크 확인"을 거친다.

## 과거 유사 태스크 확인

병렬 호출로 가는 경우에만 한다. 에이전트를 안 띄우는 간단한 태스크에서는 이 단계도 건너뛴다.

먼저 `AskUserQuestion`으로 "과거 유사 태스크도 살펴볼까요?"를 예/아니오로 묻는다. 새 기능처럼 선례가 없는 태스크에서도 단어가 조금 겹친 어중간한 후보가 나와 분석을 엉뚱한 쪽으로 끌 수 있어서, 선례가 있을 법한지는 사용자가 정한다. 아니오면 아래 검색을 모두 건너뛰고 병렬 호출로 간다.

예면 두 검색을 돌린다. 순위는 따로 나오며 섞지 않는다.

```sh
python3 ~/.claude/skills/analyze-task/tasksim.py <repo> <요구사항 원문 요약>
python3 ~/.claude/skills/analyze-task/prsim.py <저장소 경로> <요구사항 원문 요약>
```

- `tasksim.py`는 내 worklog의 task 문서를 보고, `prsim.py`는 저장소의 merge된 PR을 본다(`gh`를 못 쓰거나 PR이 없으면 커밋). 동료가 한 일이나 worklog를 쓰기 전의 일은 `prsim.py`에서만 잡힌다.
- `<repo>`는 지금 작업 중인 저장소 이름이다. worklog 폴더명(`worklog/<repo>/`)과 같다.
- `<저장소 경로>`는 지금 작업 중인 저장소의 경로다. 저장소 안에서 돌리면 `.`이다.
- `<요구사항 원문 요약>`은 원문 전체가 아니라 핵심 주제어 몇 개로 줄인 것이다. 원문을 그대로 넣으면 신호가 흐려진다.
- 라이브러리가 없거나 git 저장소가 아니어서 건너뛴다는 안내가 나오면 그대로 다음 단계로 간다. 실패로 취급하지 않는다.
- 유사도가 낮은 결과(0에 가까움)까지 끌어오지 않는다. 눈에 띄게 높은 것만 열어 본다. task 문서는 `Read`로, PR은 `gh pr view <번호>`로, 커밋은 `git show --stat <해시>`로 연다. 열어 보니 무관하면 버리고, 관련 있으면 무엇을 했는지 한두 줄로 남긴다.
- 찾은 게 있으면 두 서브에이전트 호출 프롬프트에 "참고: 과거 유사 태스크"로 함께 실어준다. PR·커밋이면 변경 파일 목록도 함께 싣는다. code-analyst가 그 목록을 `cochange.js` 입력으로 쓸 수 있다. 없으면 언급하지 않는다.
- 이건 `cochange.js`(code-analyst가 쓰는, git 커밋 기반 파일 동반 관계)와 다른 도구다. 이건 텍스트 유사도로 업무 단위 선례를 찾는다.

## 병렬 호출

**한 응답에서** 서브에이전트 2개를 동시에 호출한다. 순차로 부르지 않는다.

- [`domain-analyst`](../../agents/domain-analyst.md)
- [`code-analyst`](../../agents/code-analyst.md)

각 호출 프롬프트에 **확보한 요구사항 원문 텍스트를 그대로 실어서** 넘긴다. 링크나 파일 경로만 넘기지 않는다. 두 에이전트의 도구는 `Read`·`Grep`·`Glob`(그리고 `code-analyst`는 `Bash`)뿐이라 웹이나 Notion을 열 수 없어서, 위치만 받으면 원문 없이 분석하게 된다.

분석 범위를 좁힌 것이 있으면 함께 넘긴다. 과거 유사 태스크를 찾았으면 그것도 함께 넘긴다.

## 취합과 출력

두 결과가 다 온 뒤에 한다. 새로운 분석을 만들지 않는다.

- 마크다운 보고 하나로 낸다. 도메인 설명을 앞에, 코드 분석을 뒤에. `ReportFindings`는 쓰지 않는다.
- 보고 머리에 추정한 유형과 규모를 적는다. 코드 분석에서 드러난 변경 지점이 추정과 다르면 고친 값과 이유를 함께 적는다.
- 코드 파트의 위치는 `파일:심볼`로 쓴다. 행 번호는 쓰지 않는다.
- 두 결론이 상반되면 해소하지 말고 양쪽을 나란히 둔다. 양쪽에서 나온 "확인이 필요한 질문"은 맨 뒤에 하나로 모은다.
- **`domain-analyst`의 산출물은 최종본이 아니라, 상위가 사용자에게 풀어줄 1차 자료다.** 취합 뒤 사용자가 되묻는 후속 질의응답은 상위가 직접 한다. 서브에이전트를 다시 부르지 않는다.
- **이 단계의 산출물은 대화로만 낸다. worklog 문서를 만들지 않는다.**
- 사용자가 이어서 "설계해줘" 하면 `/task`로 넘어가고, 이 분석이 계획 섹션의 근거가 된다.
