# 태스크 사전 분석 절차

[`/development`](../development/SKILL.md)로 코드를 짜기 전 단계다. 사용자가 도메인 지식이 적어도 태스크를 이해하도록, 도메인 설명과 코드 지도를 미리 만든다.

축을 격리해 병렬로 돌리고 취합만 상위가 하는 구조는 [`review-panel`](../review-panel/SKILL.md)과 같고, 그 구조를 두는 이유는 그쪽 서두에 있다. 다만 대상을 확정하는 방식은 다르다. `review-panel`은 diff 범위를 잡고, 이쪽은 요구사항 원문을 확보한다.

## 요구사항 확보

분석은 요구사항 원문 위에서만 한다. 원문이 없으면 분석하지 않는다.

| 사용자가 준 것 | 진행 |
|---|---|
| 태스크 텍스트를 그대로 붙여넣음 | 그 텍스트를 원문으로 삼아 분석을 시작한다. |
| 링크를 주었고, 그 링크를 열 수 있음 | 읽어 온 내용을 원문으로 삼아 분석을 시작한다. |
| 링크를 주었으나, 열 수 없음 | **분석하지 않는다.** 왜 못 여는지 밝히고 원문을 붙여넣어 달라고 요청한다. |

- Notion 링크는 `notion-fetch`로 읽는다. 도구가 없거나 인증·권한 오류가 나면 "열 수 없음"이다.
- 열 수 있는지 미리 짐작하지 않는다. 한 번 시도해 보고 그 결과로 판정한다.
- **열지 못한 링크의 내용을 제목이나 URL로 미루어 지어내지 않는다.** 멈추는 것이 맞다.
- 링크로 읽어 온 경우에는 무엇을 읽었는지 한 줄로 밝히고 진행한다. 붙여넣은 텍스트는 확인이 필요 없다.
- 페이지가 크면 태스크에 해당하는 절만 추린다. 무관한 부분까지 통째로 서브에이전트에 넘기지 않는다.
- 사용자가 분석 범위를 좁혀줬으면 그것이 1순위다.

## 규모 판단

- 요구사항이 한두 문장이고 건드릴 곳이 자명하면 에이전트를 띄우지 않는다. 관련된 것만 직접 짧게 짚고 끝낸다.
- 그 외에는 병렬 호출로 간다.

## 병렬 호출

**한 응답에서** 서브에이전트 2개를 동시에 호출한다. 순차로 부르지 않는다.

- [`domain-analyst`](../../agents/domain-analyst.md)
- [`code-analyst`](../../agents/code-analyst.md)

각 호출 프롬프트에 **확보한 요구사항 원문 텍스트를 그대로 실어서** 넘긴다. 링크나 파일 경로만 넘기지 않는다. 두 에이전트의 도구는 `Read`·`Grep`·`Glob`(그리고 `code-analyst`는 `Bash`)뿐이라 웹이나 Notion을 열 수 없어서, 위치만 받으면 원문 없이 분석하게 된다.

분석 범위를 좁힌 것이 있으면 함께 넘긴다.

## 취합과 출력

두 결과가 다 온 뒤에 한다. 새로운 분석을 만들지 않는다.

- 마크다운 보고 하나로 낸다. 도메인 설명을 앞에, 코드 분석을 뒤에. `ReportFindings`는 쓰지 않는다.
- 코드 파트의 위치는 `파일:심볼`로 쓴다. 행 번호는 쓰지 않는다.
- 두 결론이 상반되면 해소하지 말고 양쪽을 나란히 둔다. 양쪽에서 나온 "확인이 필요한 질문"은 맨 뒤에 하나로 모은다.
- **`domain-analyst`의 산출물은 최종본이 아니라, 상위가 사용자에게 풀어줄 1차 자료다.** 취합 뒤 사용자가 되묻는 후속 질의응답은 상위가 직접 한다. 서브에이전트를 다시 부르지 않는다.
- **이 단계의 산출물은 대화로만 낸다. worklog 문서를 만들지 않는다.**
- 사용자가 이어서 "설계해줘" 하면 `/task`로 넘어가고, 이 분석이 계획 섹션의 근거가 된다.
