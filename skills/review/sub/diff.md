# push 전 리뷰

원격에 아직 올라가지 않은 변경 전부가 대상이다. 판단할 것은 "이대로 push해도 되는가"다.

## 범위

범위는 "커밋하고 push하면 원격에 새로 올라갈 것 전부"다. push하지 않은 커밋, 커밋하지 않은 수정, 추적되지 않은 새 파일을 모두 본다. 되묻지 않는다.

비교 기준은 아래로 정한다.

1. upstream이 있으면 `@{upstream}`이다. 아래 명령이 성공하면 upstream이 있다.

```sh
git rev-parse --abbrev-ref @{upstream}
```

2. upstream이 없으면 베이스와의 갈림점이다. 베이스는 [`git-workflow`](../../git-workflow/SKILL.md)의 "베이스 브랜치 고르기"로 정하고, 갈림점은 아래로 구한다.

```sh
git merge-base origin/<base> HEAD
```

`git diff`는 추적되지 않은 파일을 담지 않으므로, 스냅샷을 뜨기 전에 저장소 루트에서 새 파일을 intent-to-add 한다.

```sh
git add -N .
```

비교 기준과 워킹트리를 비교한다. 커밋을 주지 않고 기준만 주면 워킹트리와 비교하므로, 커밋한 것과 커밋하지 않은 것이 한 스냅샷에 함께 들어간다.

```sh
git diff <비교 기준>
```

이 출력이 스냅샷이다. 뜬 뒤 인덱스를 되돌린다.

```sh
git reset
```

- `.gitignore` 대상은 `git add -N`이 무시하므로 자동으로 범위 밖이다. 커밋에 안 올라갈 파일은 gitignore에 있어야 한다.
- `git reset`은 인덱스만 되돌리고 워킹트리는 건드리지 않는다. `-N`은 내용을 스테이징하지 않으므로 실제 커밋에 영향이 없다. 리뷰 전에 스테이징해 둔 것이 있으면 함께 풀리니 커밋 전에 다시 add 한다.
- 무엇이 범위에 들었는지는 `git status --porcelain`으로 확인한다. 표시만 하고 되묻지는 않는다.

셸 변수를 쓰지 않고 명령을 리터럴로 쓴다. Bash 호출 사이에는 셸 상태가 남지 않는다. 단일 명령으로 유지한다. `&&`·`;`·`|`로 엮으면 allowlist의 접두 규칙에 걸리지 않아 매번 승인 프롬프트가 뜬다.

## 축

세 축만 부른다. 규모가 trivial이면 [`verify.md`](../verify.md)의 "규모 판단"대로 서브에이전트를 부르지 않고 상위가 직접 본다.

- [`logic-reviewer`](../../../agents/logic-reviewer.md)
- [`impact-reviewer`](../../../agents/impact-reviewer.md)
- [`convention-reviewer`](../../../agents/convention-reviewer.md)

**부르기 전에 요구사항을 먼저 확보한다.** 현재 브랜치의 계획 문서 `requirements.md`에서 요구사항을 꺼내 세 에이전트에 실어 넘긴다. 문서가 없으면 PR 설명·커밋 메시지·이번 대화에서 모으고, 그래도 없을 때만 사용자에게 묻는다. 확보 절차는 [`verify.md`](../verify.md)의 요구사항 확보에 있다.

여기서 요구사항은 지적을 만드는 근거가 아니라 **오탐을 거르는 근거**다. 공통부 검증의 "요구사항에 명시된 동작은 버린다"가 그것으로 작동한다.

화면에 닿는 파일이 있으면 [`qa-reviewer`](../../../agents/qa-reviewer.md)를 부록으로 함께 부른다. 방금 짠 화면을 브라우저에서 무엇부터 볼지가 이 시점의 실제 필요다.

아키텍처·테스트·요구사항 축은 여기서 부르지 않는다. push 직전은 기능이 절반만 짜인 상태일 수 있기 때문이다. 아키텍처 축은 미완성을 구조 결함으로 오인하고, 요구사항 축은 아직 안 만든 것을 누락으로 자리만 잡아둔 코드를 어긋남으로 올린다. 테스트 축은 변경에 대응하는 테스트가 있는지를 완성된 단위에서 봐야 판정이 선다. push 전 범위에는 [`dev-tdd`](../../dev-tdd/SKILL.md)의 절차를 나눠 올린 테스트만 있거나 구현만 있을 수 있고, 테스트 러너가 없어 실행으로 확인하는 저장소도 있어서, 그 범위만 보면 "없다"는 오탐이 쌓인다. 셋 다 PR을 올린 뒤 [PR 리뷰](pr.md)가 완성된 단위에서 본다.

반면 `impact-reviewer`는 미완성 상태에서도 부른다. 이미 바꾼 심볼의 호출부는 실재하므로 판정에 추측이 끼지 않고, 방금 고친 것이 다른 곳을 깨뜨렸는지가 push 직전에 가장 알고 싶은 것이기 때문이다.

## 이어서

[`verify.md`](../verify.md)를 읽고 요구사항 확보부터 출력까지 그대로 진행한다. 요구사항은 사용자에게 먼저 묻지 않고 현재 브랜치의 계획 문서부터 본다.
