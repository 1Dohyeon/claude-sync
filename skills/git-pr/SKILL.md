# PR

PR 구조(단일 PR, 순차 PR, 부모 PR + 하위 PR)는 계획 단계에서 정한다. 판정 기준과 파일 세는 방식은 [`dev-plan/sub/analyze-task.md`](../dev-plan/sub/analyze-task.md)의 "규모"와 "PR 구조"에 있다. 커밋 단위는 [`git-commit`](../git-commit/SKILL.md)에 있다.

## 변경 종류와 PR 크기

| 종류      | 뜻                                                                                                        | PR 크기 기준                                                   |
| --------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 일괄 변경 | 같은 규칙의 수정을 여러 파일에 똑같이 반복한 변경(이름 바꾸기와 import 수정, 포맷터 실행, 토큰 일괄 치환) | 제한이 없다. 본문에 어떤 명령이나 규칙으로 바꿨는지 적는다     |
| 작성 변경 | 파일마다, 줄마다 다른 판단이 들어간 변경(화면·API 추가, 버그 수정, 공용 컴포넌트 prop 추가)               | 주제 하나만 담는다. 800줄 또는 20파일을 넘으면 나눌지 검토한다 |

- 일괄 변경과 작성 변경을 같은 PR에 섞지 않는다.
- 줄 수는 추가와 삭제를 합쳐 센다. 파일 수는 `analyze-task.md`의 "파일 세는 방식"으로 센다.
- 상수·목업, 동작 하나에 딸린 긴 테스트는 기준을 넘어도 나누지 않을 수 있다.
- 이 크기 기준은 규모와 별개다. 하위 PR의 규모는 리뷰 축을 정하는 데만 쓴다.

## 브랜치 계층

- 브랜치는 "베이스 → 부모 → 하위" 세 단계를 넘지 않는다. 영역별 중간 브랜치를 두지 않는다.
- 하위 PR이 너무 커지면 그 아래에 브랜치를 만들지 않고, 같은 단계의 형제 하위 PR로 나눈다.
- epic의 마일스톤은 계획 문서에만 두고 브랜치로 만들지 않는다.
- 부모 브랜치는 [`git-worktree`](../git-worktree/SKILL.md)의 "select base"로 정한 베이스에서, 하위 브랜치는 부모 브랜치에서 만든다. 만드는 순서는 `git-worktree`의 "create worktree"(메인 클론이면 `branch.md`의 "create branch")와 같다.

## 하위 PR 진행

순차 PR과 부모 PR + 하위 PR 구조에 적용한다.

| 규칙           | 내용                                                                                                                                        |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 계획           | 처음에는 마일스톤과 의존 관계만 정하고, 하위 PR은 다음 하나만 확정한다                                                                      |
| 자르는 시점    | 다른 작업이 기다리는 부분이 완성되었을 때, 주제 하나가 끝났을 때, 크기 기준에 가까워졌을 때 가운데 먼저 오는 때다                           |
| 공통 부분 먼저 | PR을 나누기로 했을 때, 여러 하위 PR이 함께 쓰는 부분(셸, 공용 입력, 규칙)은 별도 PR로 먼저 머지한다. 단일 PR 안에서는 커밋 순서로 앞에 둔다 |
| 구조 변경 먼저 | PR을 나누기로 했을 때, 기존 코드를 고치는 구조 변경은 그것을 쓰는 기능 PR보다 먼저 별도 PR로 올린다. 단일 PR 안에서는 커밋 순서로 앞에 둔다 |
| 형제가 기본    | 하위 PR은 부모에서 형제로 만든다. 다른 하위 PR의 코드가 있어야 동작할 때만 그 위에 쌓는다                                                   |
| 겹침 충돌      | 같은 파일을 고친 형제 PR은 앞 PR이 머지된 뒤 부모 기준으로 rebase해 충돌을 풀고, 빌드와 타입 검사를 다시 통과시킨다                         |
| 묶음 리뷰 요청 | 관련된 하위 PR은 링크를 한 번에 묶어 리뷰를 요청하고, 읽는 순서를 함께 적는다                                                               |
| 부분 머지      | 승인된 하위 PR부터 머지하고, 수정 요청이 온 PR만 고친다                                                                                     |
| 기획 변경      | 아직 머지하지 않은 하위 PR에 반영한다. 이미 머지된 부분이 바뀌면 그 변경을 새 하위 PR로 올린다                                              |

## 부모 브랜치 운영

| 규칙        | 내용                                                                                                 |
| ----------- | ---------------------------------------------------------------------------------------------------- |
| 베이스 반영 | 하위 PR을 하나 머지할 때마다 베이스의 변경을 부모에 반영한다                                         |
| 형제 rebase | 하위 PR을 부모에 머지하면, 진행 중인 다른 하위 브랜치는 부모 기준으로 rebase한다                     |
| 최종 PR     | 부모 PR은 모든 하위 PR이 머지된 뒤에만 베이스로 올린다. 본문은 하위 PR 목록과 통합 확인으로 구성한다 |
| 하위가 하나 | 부모 구조로 시작했는데 하위 PR이 하나로 끝나면, 부모에서 바로 베이스로 PR을 올린다                   |

## PR 본문과 머지

- PR 생성·수정은 필요하면 한다.
- PR 본문에는 이번에 한 것만 쓴다. "이 PR에 없는 것"처럼 하지 않은 일을 나열하는 절을 두지 않는다.
- 머지(`git merge`, `gh pr merge`)는 사용자가 요청할 때만 한다. 실행 전 확인은 [`settings.json`](../../settings.json)의 `permissions.ask`가 받으므로, auto mode여도 확인 창이 뜬다.
